# Decision log

Format: `- [module] decision — reasoning — alternative considered`

- [infra] Custom Postgres image extending `postgis/postgis:16-3.4` with `postgresql-16-pgvector` from PGDG — no official image ships both PostGIS and pgvector — alternative: two separate databases (rejected: cross-DB joins for parcel-scoped retrieval) or an unofficial combined image (rejected: provenance/trust).
- [infra] Extensions created via `docker-entrypoint-initdb.d` on first boot AND re-asserted `IF NOT EXISTS` in the first Alembic migration — a fresh `make migrate` must be self-sufficient on any empty DB, not only the compose one.
- [infra] Host port mapped `5433:5432` — avoids collision with a developer's local Postgres on 5432.
- [schema] Chunks carry denormalized filter fields (commune_code, language, legal_status, document_date, document_type) — retrieval must filter the space *before* vector/lexical scoring (M3.1) and exclude repealed text with no join (debrief Q9) — alternative: fully normalized, join to `documents` at query time (rejected: join before the vector scan, weaker index filtering).
- [schema] Amendment chains modeled as self-referential FKs `supersedes`/`superseded_by` on `documents` plus a `legal_status` enum — covers bonus +8 without a full version table — alternative: separate `document_versions` table (deferred: heavier than 3 weeks warrants).
- [schema] ELI stored as nullable unique key; primary key stays a UUID — communal PDFs and geodata have no ELI, so ELI cannot be a universal PK despite the spec's suggestion — alternative: ELI-as-PK for Legilux only (rejected: mixed PK strategy across one table).
- [ingestion] Plain typed Python scripts, not Prefect/Dagster/Celery — the corpus is a small serial batch; a scheduler adds ops surface with no payoff at this scale — alternative: Prefect (deferred to the 102-commune scale-out, noted in SCALING.md).
- [schema] `embedding vector(1024)` pinned to a BGE-m3 / multilingual-e5-large class model — multilingual FR/DE/LB coverage, self-hostable so indexing cost is compute not per-token API (debrief Q1) — alternative: OpenAI text-embedding-3-large 3072-d (rejected: per-token cost, larger index, no LB).
- [schema] `legal_status` includes `unknown` as the ingest-time default — honest state for freshly fetched docs whose status is not yet determined, rather than guessing in_force — alternative: default in_force (rejected: violates the no-guessing rule and risks presenting repealed text as current).
- [schema] chunks.tsv is a stored generated tsvector using the `simple` config (no stemming) — preserves article numbers, defined terms and rare tokens, which lexical legal search depends on — alternative: per-language stemmed configs (deferred to M3 if recall needs it).
- [infra] Alembic `include_object` ignores reflected objects absent from ORM metadata — stops autogenerate emitting DROP for PostGIS/tiger-geocoder tables the extension owns — alternative: drop tiger geocoder in init (rejected: brittle across base-image versions).
- [infra] Enum types created once at the top of the migration with `create_type=False` on columns — types shared by documents+chunks would otherwise CREATE TYPE twice and fail — alternative: distinct per-table enum names (rejected: duplicates the vocabulary).
- [M1] Parcels carry TWO commune codes: `cadastral_commune_code` (ACT's own PCN numbering, e.g. `001`) and `admin_commune_code` (LAU2, e.g. `0501`) — verified via `liste-communes-sections.csv` that these are genuinely different numbering systems and NOT 1:1 after historical mergers (cadastral communes 001 "Arsdorf" and its former neighbour are now both sections inside administrative commune "Rambrouch"). Cadastral code drives the commune+section+number reference search (M1.3); admin code drives which commune's PAG/bylaw applies (M2/M3 scoping) — conflating them would misattribute regulations for any merged commune — alternative: single admin-only or cadastral-only code (rejected: breaks one of the two required lookups, see debrief Q6 prep in WALKTHROUGH.md).
- [M1] `parcel_natures` / `building_natures` are reference tables (code, label, category), not Python enums — these are ACT-owned open vocabularies (~50 and ~34 values) that also carry a "category" grouping useful for map styling, unlike the small closed vocabularies (`legal_status` etc.) that justified enums in the provenance schema — alternative: hardcoded Python enum (rejected: duplicates ACT's own taxonomy and can't carry the category grouping).
- [M1] Building↔parcel modeled as a persisted `parcel_buildings` join table (parcel_id, building_id, overlap_m2), computed once at ingest via `ST_Intersects` — verified the real BATIMENTS.dbf has NO parcel FK and NO building ID at all (only `CODE_OCCUPATION` + `CODE_COMMUNE`), so a building's parcel(s) can only ever be resolved spatially, and a building can genuinely span two parcels (graded M1.3 edge case) — alternative: live `ST_Intersects` at query time (rejected: pushes a geometric computation into every side-panel request instead of paying it once at ingest) or a single nullable FK (rejected: silently wrong for the multi-parcel case).
- [M1] Address fuzzy search: `pg_trgm` GIN index on an unaccented/lowercased generated column, plus a small hand-written abbreviation table (`r.`→`rue`, `str.`→`strooss`, etc.) applied in Python at query time, not stored as a DB table — the abbreviation set is fixed and code-reviewable, not runtime data — alternative: trigram alone (rejected: weak on abbreviations, which share almost no trigrams with their expansion) or a full tsvector+trigram hybrid (rejected: more moving parts than one autocomplete field needs).
- [M1] `unaccent()` is not `IMMUTABLE` in stock Postgres, so it cannot be used directly in a generated column or a plain functional index — the migration wraps it in a small `IMMUTABLE` SQL function (`unaccent_immutable`) that pins the `unaccent` dictionary explicitly. Caught by testing the generated column, not anticipated in advance.
- [M1] Declared area (`area_declared_m2` in the M4 report schema) is honestly `null` for now — verified PCN's `PARCELLES.dbf` has exactly 7 fields (`ID_PARCELLE`, `CODE_COMMUNE`, `CODE_SECTION`, `NUMERO_PRINCIPAL`, `NUMERO_SECONDAIRE`, `LIEUDIT`, `CODE_NATURE`) and none of them is an area/superficie value. CACLR's `IMMEUBLE` file is a candidate but is an undocumented fixed-width legacy export not yet decoded — logged as an open thread, not fabricated.
- [M1] Small curated reference vocabularies (parcel/building natures, the commune registry, the cadastral↔administrative crosswalk — a few KB each, hand-verified against source) live in `backend/app/reference_data/`, tracked in git — NOT `backend/app/data/`, which `.gitignore`'s existing `data/` rule (intended for bulk cadastre/imagery dumps) silently swallows. Caught because the seed CSVs didn't show up in `git status` — alternative: a `.gitignore` exception for one subpath (rejected: more fragile than just not reusing an already-overloaded directory name).
- [M1] `section_code` widened from `VARCHAR(2)` to `VARCHAR(3)` in a follow-up migration — triggered by a seed-loader failure, root cause resolved once real parcels were ingested: `liste-communes-sections.csv` uses a DIFFERENT section-code convention (`HaA`, `HoC`, disambiguating across an administrative commune's several cadastral communes) than the real `PARCELLES.dbf` field (`CODE_SECTION`, always a single letter, scoped within one cadastral commune). `cadastral_sections` is therefore NOT joinable to `parcels.section_code` as originally assumed — kept as a standalone reference table; the section-name lookup for the M1.3 side panel is deferred rather than bridged with a guessed string transform.
- [M1] Reference-table seeding uses Postgres `INSERT ... ON CONFLICT DO UPDATE` (upsert) keyed on each table's natural PK/unique constraint, not a truncate-and-reload — re-running `make seed-reference` is a verified no-op (same row counts, confirmed by actually re-running it), matching M2.1's idempotency requirement even though this loader itself sits outside the `sources`/`documents` provenance tracking (it's static ACT/CACLR vocabulary, not a crawled, citable document).
- [infra] Added `app/core/logging.py` (structlog, JSON output) ahead of the first ingestion script that needed to log anything — enforces the "structured logs, not prints" coding standard from the start rather than retrofitting it once several scripts already use `print`.
- [M1] Ingestion downloads use data.public.lu's stable `/r/<uuid>` redirect URLs, not the dated snapshot path (`download.data.public.lu/resources/.../TIMESTAMP/file`) — the dated URL for BD-Adresses returned a live 404 mid-session because the dataset had refreshed since the URL was first captured. Caught by actually re-running the ingester days apart, not anticipated — a real illustration of why M2's crawler needs its own re-resolution logic, not hardcoded URLs, for any "weekly updated" source.
- [M1] Geodata parsing uses pyshp + shapely (pure Python), not GDAL/ogr2ogr — no system package manager step, keeps `make ingest` working with only `pip install -e .[dev]` on a clean machine. Spatial predicates (parcel↔building overlap, address→parcel containment) run as a SQL pass in PostGIS after loading, not in Python — alternative: GDAL (rejected: outside the mandatory stack, adds an undocumented system dependency).
- [M1] Buildings use scoped delete-then-reinsert per ingest run (not upsert) — the real BATIMENTS source has no natural key at all (verified: only `CODE_OCCUPATION` + `CODE_COMMUNE` + geometry), so there is nothing to upsert against. `parcel_buildings` is safe to recompute every run since it cascade-deletes with its buildings.
- [M1] Bulk inserts are batched (2000 rows/statement) — Postgres caps bound parameters at 65535 per statement, and Luxembourg City alone has enough parcels/addresses to exceed that in a single `INSERT ... VALUES`. Caught by actually running the ingester against real Luxembourg City data, not anticipated from Wiltz alone (confirms the "large, complex" profile was the right pick for the contrast).
- [M1] `parcel_buildings` requires `ST_Area(ST_Intersection(...)) > 1.0` m², not `> 0` — `ST_Intersects` is true for a mere shared-boundary touch. Caught on real data: a building appearing to span 9 parcels actually had meaningful overlap (142-420 m²) with only 3; the other 6 were floating-point slivers down to 0.0000012 m². A plain `> 0` filter would have overstated the "building spans multiple parcels" edge case with noise, not real cases.
- [testing] Tests run against the same Postgres `make ingest` populates (real Wiltz + Luxembourg City data), not a separate throwaway DB — the mandatory "e2e test hitting a real parcel" only means something if the parcel is real. Each test gets its own connection wrapped in an outer transaction, rolled back at teardown (verified: real row counts unchanged after a full test run). Tests that need to assert an expected `IntegrityError` use `session.begin_nested()` (a real SAVEPOINT) around just that insert, not the outer transaction — the first attempt called `session.rollback()` directly, which rolled back the *outer* per-test transaction itself (same underlying transaction, since the Session was bound directly to an already-open connection) and produced a `SAWarning: transaction already deassociated` at teardown; harmless here (nothing ever gets committed either way) but not the correct pattern, fixed once actually run.
- [testing] Schema-constraint tests reuse real seeded reference rows (`cadastral_communes`, `parcel_natures`) as FK targets instead of inventing fixture rows — `make seed-reference` is already a prerequisite for the app to do anything, so there is no scenario where those tests could run without it.
- [M1.2] `addresses.street_name_normalized` had NO trigram index at all until caught by actually running `EXPLAIN ANALYZE` on the search query — the design decision was documented (DECISIONS.md) but never implemented in the `Address` model. Without it: 110ms, sequential scan over all 23,680 rows. With `ix_addresses_street_name_trgm` (GIN, `gin_trgm_ops`): 12.6ms, bitmap index scan. A design decision written down is not the same as a design decision built — this is exactly why the M1.2 EXPLAIN ANALYZE requirement exists, and it earned its keep here.
- [M1.2] Address search combines three things, each covering what the others miss: `pg_trgm`'s `%` similarity operator (typos, e.g. "Lng" still matches "Lang"), a small hand-written abbreviation table applied before normalization (`r.`→`rue`, etc.), and a leading-digit split so "1 Rue du Fort Thüngen" filters on house number 1 AND fuzzy-matches the street separately, rather than fuzzy-matching the whole string as one blob. Does NOT solve full FR/DE/LB street-name variants (needs CACLR's `ALIAS.RUE` real alias data, not a synonym table) — logged as a real gap, not silently covered by the abbreviation table.
- [M1.3] `identify_by_point` returns a LIST, never a single parcel — 0 results (click missed every parcel, e.g. a road) and >1 results (click landed exactly on a shared boundary, the explicit graded edge case) are both real, honest outcomes the API surfaces rather than silently resolving by picking one.
- [M1.1] Frontend EPSG:2169 reprojection (proj4, for OpenLayers) uses PostGIS's own `spatial_ref_sys.proj4text` `towgs84` parameters (`-189.6806,18.3463,-42.7695,-0.33746,-3.09264,2.53861,0.4598`), not a plausible-looking guess — a first attempt with different (also plausible-looking) parameters was off by **108 metres** on the same known coordinate pair used for the backend's reprojection proof. Verified before writing any UI code: with PostGIS's exact parameters, proj4 agrees with the backend's PostGIS/PROJ transform to ~1.5mm. This is exactly the kind of error that would silently misidentify a parcel on every map click — caught by testing against the backend's own value, not assumed correct because the numbers "looked reasonable."
- [M1.1] The OpenLayers `View` uses an explicit `resolutions` array (metres/pixel: 200 down to 0.125), not OL's default zoom levels — OL's built-in zoom→resolution mapping assumes a Web-Mercator-like world extent, which is meaningless for a small, custom, meter-based CRS like LUREF. Caught by actually loading the map in a browser (Playwright), not by reading the code: at "zoom 15" with default levels, tile requests came back with a ~2.4m × 2.4m bbox — visibly wrong (grey tiles, nothing rendered). Same root cause as the address-search index gap: a plausible-looking default silently didn't apply to our specific setup, and only running it for real revealed that.
- [M1.1] Base layer names (`Basemap`, `ortho_latest`, `PCN`) and the working WMS endpoint (`wms.geoportail.lu/opendata/service`) were verified with a live `GetMap` request (curl, saved and viewed the PNG) before writing any React code, not assumed from the `GetCapabilities` layer list alone — confirms the endpoint actually serves imagery in EPSG:2169, not just that a layer with that name exists.
- [M1.1] Frontend verification used a real headless browser (Playwright + Chromium, installed for this purpose — no MCP/browser tool was available), not just `tsc`/`eslint`/curl. This is what caught both real bugs above (the datum shift was caught via `node -e` before any UI code existed; the resolution/zoom bug was only visible by actually loading the map and screenshotting it) plus ruled out a false alarm (orthophoto tiles appeared blank at first but were simply still loading — confirmed by waiting longer, not "fixed" by guessing at a cause).
- [infra] `.gitignore` comments must be on their own line, not appended after a pattern — `.node-local/  # comment` is parsed as one literal (and useless) pattern, not a pattern plus a comment. Caught by `git check-ignore` returning exit 1 for a path the file was supposed to exclude, not by reading the file.
- [M1.4] Real thematic overlay layers (PAG, Natura 2000, flood zones, etc.) were found by reading the *official geoportail.lu web client's own* theme config (`map.geoportail.lu/themes?interface=main&all=true`), not `GetCapabilities` — that endpoint alone doesn't surface them. Layers are addressed by a **numeric WMS ID**, not the friendly name shown in that config (`pag_pag` → `LAYERS=698`) — verified live with GetMap + GetFeatureInfo before writing any code. Full mapping + the two categories with no real layer at all (zone verte, HV electricity) in SOURCES.md.
- [M1.4] No WFS exists on `wms.geoportail.lu/public_map_layers/service` (confirmed: `SERVICE=WFS` → an OWS exception), so overlay intersects are computed by point-sampling GetFeatureInfo (parcel centroid + up to 4 boundary points) rather than a true national bulk-ingested polygon-vs-polygon test — a deliberate, user-confirmed trade-off. GetFeatureInfo's `INFO_FORMAT=application/json` unexpectedly returns the full feature **geometry**, not just attributes, so once a sample point *does* hit something, the overlap area is computed exactly via shapely against our own stored parcel geometry — only "did we find the hit at all" is approximate, not the area once found.
- [M1.4] Results are computed once per parcel and cached in `parcel_overlay_results` (unique on parcel_id+layer_code, upserted) — this external WMS is slow (~1s/request) with no server-side cache of its own, so re-querying it on every parcel-detail request would both be slow and repeatedly hit a free public server for data that can't have changed since the last request. First view of a new parcel: ~10s (18 layers × up to 5 sample points, capped at 8 concurrent requests). Every view after: ~25ms, served entirely from our own DB.
- [M1.4] A line/point-geometry overlay feature (or a polygon merely touching the parcel at a boundary, zero measure) can legitimately intersect with `overlap_m2 == 0.0`, e.g. `gas_network`'s "within 250m of a pipeline" buffer touching a parcel's corner — this is reported honestly as a real, if marginal, intersection rather than hidden; `overlap_m2` is set to `None` only when the returned feature's geometry type isn't a polygon at all (area is undefined, not just small).
- [M1.1/M1.4] Base **and** overlay layers use `ImageWMS`/`ol/layer/Image` (one request per view), not `TileWMS`/`ol/layer/Tile` — re-confirmed with real user testing: a real address ("6 Rue d'Allamont") looked visibly "misaligned" against the government's own map. Investigated properly before acting: (1) independently verified our stored coordinate against OpenStreetMap's Nominatim geocoder — agreed to ~1.5m, so the *data* was never wrong; (2) web-searched the symptom and found it's a well-documented WMS/MapServer issue (a real OpenLayers GitHub issue, #9327, describes the identical symptom — label repeat with TileWMS, gone with ImageWMS) caused by each tile being rendered independently with no awareness of its neighbours; MapServer's own fix for this (`tile_metatile_level`) is a *server*-side mapfile setting we don't control, since `wms.geoportail.lu` is a Luxembourg government service, not ours. `ImageWMS` is the documented client-side workaround when the server can't be configured — confirmed visually afterward (same address, same overlays, seams gone, labels intact). A `mapLoading` indicator was re-added (driven by `imageloadstart`/`imageloadend`/`imageloaderror` across every layer's source, keyed so multiple simultaneously-loading overlays don't fight each other) since a single request is slower than many small parallel ones.
