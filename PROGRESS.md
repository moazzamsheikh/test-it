# Progress

## 2026-09-01 — M1 foundation, M1.1-M1.5 working end-to-end

### What's done

**Foundation (verified, not just built):**
- PostgreSQL 16 + PostGIS + pgvector, custom Docker image, one-command up.
- Provenance schema (`sources`/`documents`/`chunks`) for M2/M3 — migrated, reversible.
- M1 spatial schema: communes, parcels, buildings, addresses, reference tables — 9 tables, 4 migrations, all reversible.

**Real data, not fixtures:**
- Ingested actual PCN (cadastre) + BD-Adresses for the two contrasting communes (Wiltz, Luxembourg City): **40,291 parcels, 28,891 buildings, 29,831 parcel↔building links, 23,680 addresses (99.8% resolved to a parcel)**.
- Pipeline is idempotent (`make ingest`) — verified by re-running and diffing row counts, not assumed.

**M1.2 — Address search:** live API, trigram fuzzy match + abbreviation handling + house-number parsing. **12.6ms warm** (`EXPLAIN ANALYZE`, real query).

**M1.3 — Parcel identify:** click-to-identify, cadastral-reference search, full detail (addresses, buildings, geometry). Identify returns a *list* — a boundary click can legitimately match >1 parcel, and that's surfaced honestly rather than guessed.

**M1.1 — Map UI:** Next.js + OpenLayers, working projection is EPSG:2169 (LUREF) itself — matching the official geoportail, not Web Mercator. Three real switchable WMS layers (Basemap, Orthophoto, Cadastral plan). Wired to M1.2/M1.3.

**M1.4 — Regulatory overlays:** 18 real thematic WMS layers (PAG zoning, Natura 2000, flood zones, servitudes, gas network, etc.) found by reading the official geoportail client's own theme config, not guessed. Per-parcel intersects computed via point-sampled GetFeatureInfo and cached (`parcel_overlay_results`) — first view ~10s, every view after ~25ms. Frontend: independent overlay checkboxes + a constraints panel (amber cards for what applies).

**M1.5 — Geometry analysis** (stretch, per the brief itself): road frontage onto real road-nature parcels (no external road dataset needed — ACT's own PCN data already tags ~1,915 parcels as roads), nearest-neighbour distances (min boundary-to-boundary, capped/radius-bounded), slope from a real open (CC0) 2024 LiDAR terrain model via windowed COG range-reads (no full 40GB download), and a manual-setback buildable envelope (PAG/PAP setback values aren't extractable yet — M2 hasn't started — so this is the brief's own explicit manual-input escape hatch, not a guess). All four verified live against real parcels, cached where the source is external/slow (slope).

**Quality bar:** 32 automated tests (schema constraints + real-data end-to-end + API), all passing. `mypy --strict` / ruff / black / ESLint / `tsc --strict` all clean. Verified in an actual headless browser (Playwright), not just linters.

**A serious bug caught by a user report, not by testing:** the map rendered a real address ("8 Rue Beck") ~15km from its true location. Investigation traced it to WMS 1.3.0 + EPSG:2169's registered axis order (Northing,Easting, confirmed against the EPSG registry) being silently mishandled — affecting not just map rendering but every M1.4 regulatory-overlay computation, since the same bug was in the backend's GetFeatureInfo point-sampling. Fixed by downgrading to WMS 1.1.1; the entire overlay cache was purged and recomputed. Full writeup in DECISIONS.md and WALKTHROUGH.md — flagged prominently because it's the most consequential bug found in the project so far, and because catching it required following a visual bug report to a backend correctness issue the user never mentioned.

### Two real bugs worth mentioning (both caught by testing, not code review)
- A guessed coordinate-reprojection parameter looked entirely reasonable and was **108 metres wrong** — would have silently misidentified parcels on every map click. Caught by checking it against the backend's own verified transform before writing any UI code.
- A missing database index meant address search was doing a full table scan (110ms) despite the design doc saying otherwise — a decision that was written down but never actually implemented. Caught by running `EXPLAIN ANALYZE`, not by reading the code.

Both are fixed, and both are logged in `DECISIONS.md` along with ~30 other decisions and the reasoning behind them.

### Known gaps (deliberate, not hidden)
- No declared/legal parcel area source found yet in PCN — reported honestly as "not extracted" rather than guessed.
- Address search doesn't yet cover full FR/DE/LB street-name aliasing (only common abbreviations) — real alias data exists (CACLR) but isn't ingested yet.
- No `zone_verte` or HV electricity easement overlay layer — searched exhaustively across the full 1437-layer geoportail theme tree, neither exists there as a real layer.
- Buildable envelope uses one manual uniform setback, not real PAG/PAP values (M2 hasn't ingested legislation yet).
- M2-M5 (legislation ingestion, chatbot, PDF report, procedure assistant) not started.

**M2 — PAG/PAP zoning (partial), from a real requirement dictated via video, not the assessment PDF:** the user shared three screen-recording transcripts demonstrating a real Luxembourg zoning-lookup workflow (PAG written + graphic parts, PAP "Quartier Existant" sub-variants, per-commune sourcing). **M2 — real COS/CUS/CSS/DL planning coefficients**, prompted by a direct follow-up question ("retrieve the information for CUS, COS, CSS, DL for a given PAP NQ"). ## 2026-09-06/08 — Per-parcel overlay document retrieval: Tier 1 complete, Tier 2 started

Prompted by a direct question: is per-parcel retrieval of the *actual regulatory text* behind M1.4's 16 non-PAG/PAP overlay categories (environnement, archéologie, eau PDFs, etc.) done — only "intersects yes/no" facts existed, no real ingested text. Researched all 16 categories via 5 parallel background agents and tiered them by real feasibility (single-document / per-instance-linkable / needs-more-research / genuine-gap) rather than assuming uniform difficulty — full breakdown in DECISIONS.md. User chose Tier 1 first.

**Tier 1 (this increment):** the 4 real sectoral plans that are each governed by exactly one règlement grand-ducal — Plan directeur sectoriel logement (PSL), transports (PST), zones d'activités économiques (PSZAE), paysages (PSP) — now carry a real, ingested document citation (title + Legilux source URL) on every parcel's constraint list, whether or not that parcel intersects the layer (the RGD governs the whole sectoral plan, not just an intersecting feature). Built a reusable Legilux "richtext" HTML extractor (`ingestion/legilux_extraction.py`, verified reusable across all 4 real documents — 10/8/12/16 real articles each, no fabrication), a shared `get_document_reference` helper with an explicit single-chunk-vs-multi-chunk citation rule (single article shown inline, matching PAG's existing behavior; multi-article RGDs show only the document-level citation, since dumping 8-16 articles into a constraint card isn't usable), and a config-driven ingestion script (`make ingest-overlay-documents`) following the same idempotent `Source`/`Document`/`Chunk` pattern as every other ingestion script in this project. Verified live end-to-end: real API response for "8 Rue Beck" now shows all 4 Tier-1 layers with a real document citation. 2 new tests (real-parcel document presence + real-parcel layers-without-a-document-url stay `None`), 46 total, all passing; `mypy`/`ruff`/`black` clean.

**Findel airport servitude RGD:** found and verified the exact Legilux URL (règlement grand-ducal du 17 mai 2006, POS "Aéroport et environs") from the secondary government page found earlier, confirmed it's genuinely the right legal basis by reading the real extracted articles (Art. 19-28 are the height/radio-navigation servitude clauses the `findel_servitude` WMS layer represents, not just a same-topic-sounding document), and ingested it through the same extractor/pipeline unchanged (33 real articles, zero code changes needed — a second real document proves the extractor generalises). Verified live. 1 new test, 47 total.

**Flood HQ20/HQ100 — Tier 1 complete, re-scoped from the original plan:** the "PGRI" single-document assumption from the earlier research pass turned out to be wrong — checked properly and found the real legal basis is a *separate règlement grand-ducal per river basin*, not one national document. Caught and corrected an error along the way: an AI-summarized fetch of the government's watercourse-legislation page had misattributed the Wiltz RGD's document number; re-verified by fetching the real page directly and reading its real link list, then confirmed the correct document numbers by fetching and extracting each candidate RGD's actual title. Presented this as a real scope decision to the user (per the project's standing rule for design-weight choices) rather than silently reinterpreting Tier 1 — chose a static per-commune mapping over chasing a GIS attribute or deferring the gap. Verified for both target communes against the real government source: Luxembourg City (Alzette) → RGD 30 March 2022 a188; Wiltz → RGD 30 March 2022 a187. `OverlayLayer` gained `document_url_by_commune`; the ingestion script dedupes by URL (both flood layers share one RGD per commune) so each unique document is fetched once, not twice — verified live via the ingestion log. Verified live end-to-end: Luxembourg City and Wiltz parcels each resolve to their own, different, correct RGD. 1 new test (both communes + a same-document guard), 48 total, all passing. **Tier 1 is now fully complete** (6 real documents: 4 sectoral plans + Findel + 2 flood RGDs).

**ZPIN dynamic per-feature document linking — Tier 2, first item:** unlike Tier 1's static per-layer documents, ZPIN's real GIS attributes carry a direct `lien_legilux` link per reserve (verified live) — meaning any of Luxembourg's real nature reserves can be auto-linked, not just ones manually discovered near our 2 target communes. Checked whether Natura 2000 (the other Tier-2 item) has the same mechanism before assuming so — it doesn't (only `SITECODE`/`SITENAME`, no link field), so it still needs the static lookup table originally planned. Discovered the `legilux.public.lu` → `data.legilux.public.lu` URL transform is fully mechanical (confirmed across 8 real documents, no exceptions), removing the need to hand-verify each ZPIN document's URL. Presented the implementation choice to the user (static mapping vs. dynamic lazy ingestion) — chose dynamic: the first real parcel to intersect a given reserve triggers a live fetch+ingest, cached on a new `parcel_overlay_results.document_id` column (migration, upgrade/downgrade both verified) so later parcels hitting the same reserve reuse it instantly. Verified live end-to-end: two real parcels intersecting the real "Gréngewald" reserve both resolved to the identical ingested document, second lookup ~76ms (no re-fetch). 3 new tests (URL-transform unit test + 2 real-parcel tests using the already-cached document, matching this project's existing style of not hitting live external services on every test run), 51 total, all passing.

**M1.3 gap closed — cadastral-reference search UI:** found while trying to give concrete live-test steps for the ZPIN feature that `findParcelByReference` (built and tested since the M1 foundation) was never actually wired to a frontend form — only address search and map-click existed. **Natura 2000 static SITECODE table — Tier 2 complete:** parsed `environnement.public.lu`'s real Natura 2000 site table myself (raw HTML, not an AI summary — after the flood-zone episode, that distinction is now standard practice for anything with a specific number attached) to find the real RGD for each of 8 sites confirmed to intersect our two target communes (5 habitats, 3 birds). Verified live: 7 of 8 sites resolved against a real intersecting parcel, including one real parcel that independently intersects both a habitats and a birds site. The 8th site is correctly ingested but no real intersecting parcel could be found within reasonable effort — reported honestly as unconfirmed. 3 new tests, 54 total, all passing. **Tier 2 (ZPIN + Natura 2000) is now complete.**

**Tier 3/4, at the user's request:** re-checked each remaining overlay category's real `GetFeatureInfo` attributes directly rather than trusting the original research pass's classification as final. Two turned out to be cheap wins, reusing the exact ZPIN dynamic-linking mechanism unchanged (one-line config additions, no new code): **drinking-water protection zones** (a real per-feature Legilux link, `'Publication du règlement grand-duca'` — the government's own attribute name is missing a trailing "l", verified live) and **POS perimeters** (`LienMemori`, resolving to a real 2020 amending RGD for the Findel "Aéroport et environs" zone — distinct from, but consistent with, the static Findel-servitude citation on a different layer). User-confirmed live in an actual browser afterward (via the cadastral-reference search UI): both citations rendered with the exact expected real Legilux "Full text" URLs — the first real browser confirmation of the citation-rendering frontend work this session (prior verification had only been server-side, since no browser/node access was available in this environment).
