## 2026-09-01 — M1 foundation, M1.1-M1.5 working end-to-end

### What's done

**Foundation (verified, not just built):**
- PostgreSQL 16 + PostGIS + pgvector, custom Docker image, one-command up.
- Provenance schema (`sources`/`documents`/`chunks`) for M2/M3 — migrated, reversible.
- M1 spatial schema: communes, parcels, buildings, addresses, reference tables — 9 tables, 4 migrations, all reversible.

**Real data, not fixtures:**
- Ingested actual PCN (cadastre) + BD-Adresses for the two contrasting communes (Wiltz, Luxembourg City): **40,291 parcels, 28,891 buildings, 29,831 parcel↔building links, 23,680 addresses (99.8% resolved to a parcel)**.
- Pipeline is idempotent (`make ingest`) — verified by re-running and diffing row counts, not assumed.

**M1.2 — Address search:** live API, trigram fuzzy match + abbreviation handling + house-number parsing. **12.6ms warm** (`EXPLAIN ANALYZE`, real query).

**M1.3 — Parcel identify:** click-to-identify, cadastral-reference search, full detail (addresses, buildings, geometry). Identify returns a *list* — a boundary click can legitimately match >1 parcel, and that's surfaced honestly rather than guessed.

**M1.1 — Map UI:** Next.js + OpenLayers, working projection is EPSG:2169 (LUREF) itself — matching the official geoportail, not Web Mercator. Three real switchable WMS layers (Basemap, Orthophoto, Cadastral plan). Wired to M1.2/M1.3.

**M1.4 — Regulatory overlays:** 18 real thematic WMS layers (PAG zoning, Natura 2000, flood zones, servitudes, gas network, etc.) found by reading the official geoportail client's own theme config, not guessed. Per-parcel intersects computed via point-sampled GetFeatureInfo and cached (`parcel_overlay_results`) — first view ~10s, every view after ~25ms. Frontend: independent overlay checkboxes + a constraints panel (amber cards for what applies).

**M1.5 — Geometry analysis** (stretch, per the brief itself): road frontage onto real road-nature parcels (no external road dataset needed — ACT's own PCN data already tags ~1,915 parcels as roads), nearest-neighbour distances (min boundary-to-boundary, capped/radius-bounded), slope from a real open (CC0) 2024 LiDAR terrain model via windowed COG range-reads (no full 40GB download), and a manual-setback buildable envelope (PAG/PAP setback values aren't extractable yet — M2 hasn't started — so this is the brief's own explicit manual-input escape hatch, not a guess). All four verified live against real parcels, cached where the source is external/slow (slope).

**Quality bar:** 32 automated tests (schema constraints + real-data end-to-end + API), all passing. `mypy --strict` / ruff / black / ESLint / `tsc --strict` all clean. Verified in an actual headless browser (Playwright), not just linters.

**A serious bug caught by a user report, not by testing:** the map rendered a real address ("8 Rue Beck") ~15km from its true location. Investigation traced it to WMS 1.3.0 + EPSG:2169's registered axis order (Northing,Easting, confirmed against the EPSG registry) being silently mishandled — affecting not just map rendering but every M1.4 regulatory-overlay computation, since the same bug was in the backend's GetFeatureInfo point-sampling. Fixed by downgrading to WMS 1.1.1; the entire overlay cache was purged and recomputed. Full writeup in DECISIONS.md and WALKTHROUGH.md — flagged prominently because it's the most consequential bug found in the project so far, and because catching it required following a visual bug report to a backend correctness issue the user never mentioned.

### Two real bugs worth mentioning (both caught by testing, not code review)
- A guessed coordinate-reprojection parameter looked entirely reasonable and was **108 metres wrong** — would have silently misidentified parcels on every map click. Caught by checking it against the backend's own verified transform before writing any UI code.
- A missing database index meant address search was doing a full table scan (110ms) despite the design doc saying otherwise — a decision that was written down but never actually implemented. Caught by running `EXPLAIN ANALYZE`, not by reading the code.

Both are fixed, and both are logged in `DECISIONS.md` along with ~30 other decisions and the reasoning behind them.

### Known gaps (deliberate, not hidden)
- No declared/legal parcel area source found yet in PCN — reported honestly as "not extracted" rather than guessed.
- Address search doesn't yet cover full FR/DE/LB street-name aliasing (only common abbreviations) — real alias data exists (CACLR) but isn't ingested yet.
- No `zone_verte` or HV electricity easement overlay layer — searched exhaustively across the full 1437-layer geoportail theme tree, neither exists there as a real layer.
- Buildable envelope uses one manual uniform setback, not real PAG/PAP values (M2 hasn't ingested legislation yet).
- M2-M5 (legislation ingestion, chatbot, PDF report, procedure assistant) not started.

## M3 — Retrieval and chatbot (this pass)

Picked up from the minimal lexical-only retrieval core built earlier. Built the rest of M3 end to end: hybrid retrieval, LLM-based reranking, a real grounded/cited chat pipeline, parcel-scoped conversation memory, a chat UI, and an extended golden-set eval covering both retrieval and generation — the two things M3.4 actually asks for.

**LLM provider — a real environment constraint, not a preference.** Planned self-hosted embeddings (BGE-m3 class, per the schema's own 1024-d pin) and a cross-encoder reranker. Verified, not assumed, that this environment's Python (3.14) has zero PyPI wheels for `torch`/`onnxruntime` — both `sentence-transformers` and `fastembed` fail to install with `ResolutionImpossible`. Pivoted both embeddings and reranking onto Gemini (the user's chosen provider, key added to `.env`): `gemini-embedding-001` at `output_dimensionality=1024` keeps the existing schema/migration untouched, and LLM-based reranking is one of the brief's own explicitly sanctioned options. Built a real `LLMProvider` abstraction (`app/services/llm/`) — `GeminiProvider` (real calls) and `ExtractiveProvider` (a genuine, tested fallback: no LLM, assembles a real cited answer directly from retrieved passages, with a real lexical-overlap relevance heuristic, not a naive passthrough that would have silently broken the refusal guarantee — caught and fixed while writing tests, see DECISIONS.md) behind one Protocol, selected by a single factory function — the actual "swap models without touching business logic" requirement.

**Real, live environment friction, worked through rather than around:** this Google account's free-tier quota for `gemini-embedding-001` specifically is tight enough that a full 1,689-chunk backfill repeatedly hit sustained 429s even at 20-30s spacing with generous retries — confirmed via direct probing, not assumed. Rather than block on it, made the whole system resilient to it instead: `ingestion/embed_chunks.py` now skips a failing batch and moves on (M2.1's "resilient, never aborts the run" applied to an API-based step), and `hybrid_search` itself degrades to lexical-only mid-request if the live embedding call fails, with a short fast-fail retry budget on that path specifically so a chat user never waits minutes for a fallback. The dense embedding *mechanism* is verified correct independent of the quota fight — real pgvector cosine-ordering tests against hand-crafted vectors, and a live end-to-end proof once ~64 real chunks got embedded before the quota tightened. A patient backfill keeps running in the background; EVAL.md discloses exactly how much of this run's numbers reflect lexical vs. dense.

**Hybrid retrieval (M3.1)**: `app/services/retrieval.py` now does real Reciprocal Rank Fusion over lexical (existing `ts_rank_cd`) and dense (pgvector cosine) candidate lists — RRF chosen because the two scores live on incomparable scales with no principled way to sum them directly. Metadata filtering (commune scoping + `legal_status` exclusion) is a shared SQL WHERE clause applied to both candidate queries before scoring, per the brief's explicit wording, with `include_national` ORing in commune-agnostic national legislation alongside an exact commune match. Multilingual handling: extended the stopword list to FR/DE/EN and added real EN/DE/LB questions to the golden set that exercise cross-lingual retrieval against the French-only corpus — LB explicitly disclosed as a weaker case (no dedicated model, cross-lingual/lexical proximity only).

**A real, serious bug found by exercising this for the first time, not by inspection:** PAG written/graphic documents (`ingest_pag_zones.py`) never had `commune_code` set at all, despite it being available at every call site — invisible until M3's commune-scoped retrieval actually queried it live. Concrete effect: a chat question about a real Schengen parcel surfaced Luxembourg City's PAP QE regulations as citations, exactly the cross-commune leakage M3.1's own brief text warns against. Fixed at the source (both the written and graphic document paths — the second one needed a follow-up fix after the first re-ingestion run showed it was incomplete), backfilled retroactively for all 8 communes via a re-run of `make ingest-pag-zones`, plus a one-time manual cleanup for 77 documents orphaned under a since-superseded dated URL. Proven with a real-data regression test harder than a title check: all 8 communes' building bylaws share the identical `Document.title`, so the test asserts on `commune_code` and a real commune-exclusive fact (Differdange's "pompes à chaleur" article) instead.

**Reranking (M3.1)**: LLM-based (Gemini, structured JSON output, not regex-parsed free text) over the fused candidate set — the environment constraint above rules out a cross-encoder, and the brief explicitly allows this alternative. `ExtractiveProvider`'s equivalent is a real lexical-overlap score, not a stub.

**Grounded chat (M3.2/M3.3)**: `app/services/chatbot.py` is the full pipeline — hybrid retrieval, rerank, a deterministic pre-generation refusal check (never asks the LLM's own judgement whether to refuse), numbered-source assembly mixing retrieved text with M1/M2 geospatial facts for the selected parcel, generation with inline `[n]` citations, and citation-marker extraction that only ever resolves against the real numbered-source list the model was actually given (never trusting a freeform citation). A real correctness bug was caught and fixed *before* it shipped, while designing the tests: checking only the reranked text score for refusal would have wrongly refused a purely-geospatial question with a real answer available from cadastral data alone — refusal now fires only when both the text score is weak AND no geospatial facts exist. Repealed/superseded provisions are excluded from retrieval at the SQL level (never a candidate at all); `unknown`/`draft` chunks are annotated inline so the model hedges rather than asserts them as settled law. Conversation memory is a real Postgres table (`chat_messages`), not an in-process dict that `uvicorn --reload` would wipe constantly in dev; `session_id` is client-generated, matching the brief's explicit no-auth scope. A real live bug surfaced by manual testing (not anticipated): Gemini sometimes combines two citations into one bracket ("[1, 2]") despite prompt instructions — the original single-digit regex silently dropped the second citation; fixed and regression-tested.

**Chat UI (M3.3)**: a minimal `ChatPanel.tsx` added alongside the existing parcel panel — message list, inline citation links, a client-generated session id in `localStorage` for cross-request conversation memory. Not polished (explicitly not required), but functional and wired to the real endpoint end to end, verified live via curl and the real API (refusal on an off-topic question, correct multi-citation extraction, correct geospatial-fact surfacing on a real Schengen parcel with an honest "I don't have a source for the height limit" answer where the corpus genuinely has no data).
